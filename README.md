
# Merge(インターン生×企業 マッチングサービス)

インターン生と企業をつなぐ、スカウト型マッチングサービスです。
企業が気になる学生に直接スカウトを送れるほか、学生側から求人に応募することもでき、双方向のコミュニケーションをチャットで行うことができます。

##  開発の背景・設計思想

本アプリは、単に求人情報やプロフィールを登録・閲覧するだけでなく、**「企業と学生が『なぜマッチするのか』を深掘りできること」**を最重要視して設計しました。

* **企業の視点:** 学生の表面的なスキルだけでなく、GitHubでの活動（継続性）やポートフォリオといった「実際のプロセスやアウトプット」を見て評価したい。
* **学生の視点:** 単なる条件面だけでなく、企業のカルチャーや「どんな技術スタックを使っているか」を重視して働く環境を選びたい。

この双方向のニーズを満たし、入社後のミスマッチを防ぐ解像度の高いマッチングを生み出すため、プロフィールの項目設計や、文脈（スカウト/応募）を分けたチャット機能などを実装しています。

##  主な機能

###  インターン生向け
* **プロフィール作成・編集**: 自己紹介・大学・GitHubリンクなどの管理
* **求人一覧の閲覧・応募**: 企業が掲載した求人へのダイレクトな応募
* **スカウト受信**: 企業から届いたアプローチの確認
* **チャット機能**: スカウト・応募それぞれの文脈に応じたチャットルームでのやり取り
* **未読通知**: 未読バッジによる新着メッセージのリアルタイム通知

###  企業向け
* **プロフィール・求人管理**: 企業情報および求人情報の作成・編集・管理
* **インターン生一覧・詳細閲覧**: 登録されている学生のプロフィール検索・閲覧
* **スカウト送信**: 気になる学生への直接スカウト送信
* **チャット機能**: 応募者およびスカウトした学生との個別チャット
* **未読通知**: 未読バッジによる新着メッセージのリアルタイム通知

##  工夫した点・こだわったポイント

### 1. ユーザー体験（UX）を意識した UI 設計
* **直感的なテーマカラーの使い分け**
  企業側は「**紫**」、インターン生側は「**青（Sky）**」とテーマカラーを明確に分けています。マイページ・チャット画面の吹き出し・送信ボタンにいたるまでこのルールを統一しており、ユーザーが自分の立場を画面上で直感的に把握できるよう設計しました。
* **新着メッセージの「未読バッジ」機能**
  チャット画面を開かなくても新着メッセージに気づけるよう、マイページの応募一覧・スカウト一覧に未読バッジを表示しています。データベースの `is_read` カラムと送信者のロール（`is_from_company`）を組み合わせて判定し、自分宛ての未読メッセージが存在する場合にのみバッジが表示される実装になっています。

```ruby
# 学生側：企業からの未読メッセージがあるか判定
has_unread = entry.entry_messages.where(is_from_company: true, is_read: false).exists?
```

### 2. フロントエンドとバックエンドの堅牢な API 連携
* **`X-User-Id` ヘッダーを用いたデータ通信**
  URL にユーザー ID を直接含めるのではなく、リクエストヘッダーの `X-User-Id` でユーザーを識別する設計にしました。Rails 側でヘッダーから送信者を特定し、企業・学生それぞれの権限に応じた適切なデータのみを返す処理を実現しています。

```typescript
// フロントエンド：ヘッダーにユーザーIDを付与
const authHeaders = {
  "Content-Type": "application/json",
  "X-User-Id": userId,
};
```

```ruby
# バックエンド：ヘッダーから送信者を特定してデータを返す
def current_user_id
  request.headers["X-User-Id"]
end
```

* **データ不在時の適切なエラーハンドリング**
  「登録直後でプロフィールデータがまだ存在しない（404 Not Found）」ケースでも画面がクラッシュしないよう、フロントエンド側でレスポンスのステータスコードごとに処理を分岐しています。単にエラー画面を出すのではなく、空の入力フォームを提示してユーザーの次のアクションへスムーズに誘導する設計にしました。

### 3. 拡張性を意識したデータベース設計
* **アカウント（User）とプロフィール（Profile）の分離**
  認証やロール管理を担う `User` モデルと、具体的な情報を持つ `InternProfile` / `CompanyProfile` モデルを分けて設計しました。初期登録のハードルを下げつつ、プロフィール情報は後から柔軟に更新できる構造になっています。
* **チャット文脈の分離管理**
  チャット機能も「スカウト経由のチャット（`Scout` ➔ `Message`）」と「応募経由のチャット（`Entry` ➔ `EntryMessage`）」を完全に分離しており、それぞれの文脈に応じた適切なデータ管理を可能にしています。

### 4. パフォーマンスを意識した N+1 問題の解消
* **メモリ上での配列照合によるクエリ最適化**
  企業側が「インターン生一覧」を取得する際、各学生に対して「すでに自社がスカウト済みか」を判定する必要があります。ここで、学生一人ひとりに対して `Scout` テーブルへ都度クエリを発行すると **N+1問題** が発生し、パフォーマンスが著しく低下してしまいます。
  これを防ぐため、事前に自社がスカウトした学生のID一覧を `pluck` で一括取得（1クエリ）し、Rubyのメモリ上で `include?` を使って判定するロジックを実装しました。これにより、データ量が増えてもデータベースへのクエリ数を最小限（2回）に抑える設計にしています。

```ruby
# 1. 先に「自社がスカウトした学生のID」をまとめて一括取得（DB通信1回）
scouted_intern_user_ids = Scout.where(company_user_id: current_user_id).pluck(:intern_user_id)

result = intern_profiles.map do |profile|
  # 2. 手元の配列(メモリ上)で照合し、ループ内の余計なDBクエリを防止（DB通信0回）
  profile.as_json.merge(scouted: scouted_intern_user_ids.include?(profile.user_id))
end
```

## 🚀 環境構築・ローカルでの起動方法

リポジトリをクローンした後、ターミナルを2つ開き、フロントエンドとバックエンドをそれぞれ起動してください。

### 1. バックエンド (Ruby on Rails) の起動
1つ目のターミナルで以下のコマンドを順に実行します。

```bash
# バックエンドのディレクトリに移動
cd backend

# 依存関係（Gem）のインストール
bundle install

# データベースの作成とマイグレーションの実行
rails db:create db:migrate

# 初期データ（シードデータ）の投入
rails db:seed

# 開発サーバーをポート3001で起動
rails s -p 3001
###  バックエンド (Ruby on Rails)
```bash
cd backend
bundle install
rails db:create db:migrate db:seed
rails s -p 3001
```

### フロントエンド (Next.js)
```bash
cd frontend
npm install
npm run dev
```

アプリは `http://localhost:3000` で起動します。

###  動作確認
このアプリケーションは、ブラウザのローカルストレージを使用してログイン状態を管理しています。
複数の役割（企業とインターン生）を同時にテストしたい場合は、**「通常モードのブラウザ」と「シークレットモード（プライベートブラウザ）」**を併用することで、セッションを分けてスムーズに動作確認が可能です。
